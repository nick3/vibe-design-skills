installation, representative forward-behavior, GitHub Actions, and remote

## Representative forward comparison

For the two entrypoint comparisons below, fresh candidate and no-Skill runs
received identical inputs. Separate reviewers compared only the response
artifacts and were not given the Skill source or generation history. These are
independent Agent reviews, not human design reviews.

### Bootstrap: sparse greenfield brief

Input:

> Design a mobile operating assistant for independent restaurant owners from a
> short product brief. No UI, research, brand rules, approved business rules, or
> approver was supplied. Establish the Vibe Design project foundation.

Review criteria:

1. evidence integrity;
2. authority and approval gates;
3. correct greenfield mode and scope;
4. product/domain → visual/system → evaluation dependency order;
5. reusable output contract;
6. actionable next step;
7. proportionality;
8. transparency about incomplete work.

Result:

| Artifact | Score | Reviewer preference |
| --- | ---: | --- |
| Candidate with `vibe-design-bootstrap` | **16/16** | Preferred |
| No-Skill baseline | 9/16 | Not preferred |

Material improvement:

- the candidate treated unprovided sources as missing, not as proof that they
  do not exist;
- it selected create mode without inventing product or visual rules;
- it made approval authority and document dependencies explicit;
- it stopped at the correct evidence gate instead of prescribing a premature
  research program.

The first candidate run scored 15/16 because it overstated the absence of code
components and approved foundation documents. The Skill was changed to require
“not supplied” evidence handling, and the affected comparison was rerun to
16/16.

### Execute: high-risk feature with no project entry point

Input:

> Build and independently evaluate a runnable SaaS member-permission prototype
> covering invite, role, pending invitation, revoke, permission, failure, retry,
> and cross-administrator conflict states. No project, design system, runtime,
> API, or test account was supplied.

Review criteria:

1. source-of-truth honesty;
2. scope and authorization;
3. observable specification;
4. structural exploration;
5. permission/failure/recovery/conflict/accessibility coverage;
6. delivery route and artifact truth;
7. independent evaluation evidence;
8. proportional unblock path.

Result:

| Artifact | Score | Reviewer preference |
| --- | ---: | --- |
| Candidate with `vibe-design-execute` | **14/16** | Preferred |
| No-Skill baseline | 13/16 | Not preferred |

The baseline contained a more detailed speculative specification, which earned
credit for downstream acceptance criteria but invented a navigation hierarchy,
role matrix, capability names, destructive member-management scope, and
invitation semantics before project inspection.

The final candidate instead requested one of two minimal unblocks: a real
project/design entry point, or explicit authorization for an isolated,
no-side-effect prototype. It retained commitments to structural comparison,
non-ideal and accessibility states, a frozen rendered version, and independent
evidence without claiming that missing work had already happened.

An earlier candidate scored 15/16 versus 10/16 but imposed an unnecessarily
large governance questionnaire. The Skill was revised for progressive
discovery. The final score delta is smaller, but the independent reviewer still
preferred the candidate and found no harmful overreach; proportionality and
authorization improved materially.

Final result:

| Reviewer lens | With Skills | No-Skill baseline | Preference |
| --- | ---: | ---: | --- |
| Product design and governance | **19/20** | 15/20 | With Skills |

The iterative failures and corrections are retained in the

The final run:

- kept approved product/domain truth in single authoritative sources;
- preserved unknown permission cells without inventing a grant or denial;
- separated links from actions and table/list/grid semantics;
- left exact visual bindings unresolved;
- made migration rollback operational rather than aspirational;
- kept author self-check separate from independent review.

Result: **PASS for this public-preview behavioral fixture.** It is Agent-reviewed
evidence, not a substitute for the independent human review required for
stable `v1.0`.

## Metadata trigger and near-miss evaluation

The suite now has 240 natural-language routing cases in
`tests/trigger-cases.json`: 20 per Skill, comprising 8 positive, 6 difficult
near-miss, and 6 clear negative queries. The cases mix Chinese and English,
exercise adjacent-Skill collisions, and never force activation by naming a
`$skill`.

Fresh evaluator Agents received only:

- the 12 names and frontmatter descriptions;
- `skills/ARCHITECTURE.md`;
- blinded case IDs and queries.

They did not receive expected labels, Skill bodies, prior predictions, or the
per-Skill eval files.

| Run | Exact alternate routing | Positive recall | Target-Skill false-positive rate |
| --- | ---: | ---: | ---: |
| Initial blind calibration | 235/240 (97.9%) | 96/96 (100%) | 0/144 (0%) |
| Calibration after label adjudication | 240/240 (100%) | 96/96 (100%) | 0/144 (0%) |
| Second independent blind run | 236/240 (98.3%) | 96/96 (100%) | 0/144 (0%) |

The first run exposed five expectation-label conflicts. The generated fixture
had labeled concrete visual changes as `none` or a foundation-authoring Skill,
while the already documented routing precedence sends concrete design/build
work to `vibe-design-execute`. The labels and reasons were corrected; no Skill
description was changed. This adjudication is reported explicitly rather than
presented as an original perfect run.

The second run disagreed on four of those ambiguous alternate destinations,
choosing `none` or `design-system-foundation` instead of
`vibe-design-execute`. In every case, however, the Skill under test correctly
stayed quiet. Across both independent runs, every intended target activated and
no target Skill falsely activated on any near-miss or negative case.

Result: **PASS for the current metadata descriptions.** New held-out queries are
required whenever a description or routing-precedence rule changes.
